## 3. Runtime structure

The whole application is one scene tree that never gets unloaded:

```
Minigames (Node2D, minigames.gd)
├── Control            ← main menu; hidden while a game runs
│   ├── VBoxContainer  ← PONG / BREAKOUT / PLATFORMER / SHOOTER /
│   │                    FLAPPER / 2048 / SNAKE buttons
│   ├── QUIT
│   └── speed_typing (demo)
├── Games              ← exactly zero or one instantiated minigame
└── Pause_menu         ← global overlay, hidden by default
```

Plus the `GameState` autoload, which sits outside the scene as a singleton.

### Scene lifecycle

```
Button pressed ─▶ minigames.gd::_on_<game>_pressed()
                        │
                        ▼
              GameState.enter("<key>")
                        │  scenes[key].instantiate()
                        │  MINIGAMES.menu.visible = false
                        ▼
              MINIGAMES.games.add_child(minigame)
                        │  minigame._ready() registers itself:
                        │      GameState.breakout = self   (etc.)
                        ▼
                 …gameplay…
                        │
                        ▼
              GameState.exit()   ← from pause menu, high score panel, or game over
                        │  MINIGAMES.menu.visible = true
                        ▼
              games.get_child(0).queue_free()
```

All minigame scenes are eagerly `load()`ed into `GameState.scenes` when the singleton
initialises, so `enter()` is an instantiate, not a disk read.

## 4. `GameState` — the singleton

`game/game_state.gd` is the only globally reachable object and carries five distinct
responsibilities.

**a) Scene routing.** The `scenes` dictionary maps a string key to a `PackedScene`, and
`enter()` / `exit()` swap the menu for a game instance. Keys currently registered:
`pong`, `breakout`, `platformer`, `shooter`, `flapper`, `2048`, `snake`,
`speed_typing`.

**b) Live object references.** `MINIGAMES`, `pause_menu`, `pong`, `breakout`,
`platformer`, `shooter`, `speedtyping`. Each node assigns itself in `_ready()`. This is
how a `BreakoutBall` reaches its game (`GameState.breakout.player.position`) without
walking the tree.

**c) Global input.** `_input()` on the singleton handles `ESC`: it toggles
`get_tree().paused`, shows `pause_menu`, and relabels the exit button `"menu"` or
`"home"` depending on whether the platformer is inside a level. `F11` fullscreen
toggling lives on `minigames.gd` instead.

**d) High scores.** One `Array` per game — `breakout_highscores`, `shooter_highscores`,
`flapper_highscores`, `game_2048_highscores`, `snake_highscores` — each holding entries
of the shape `["ABC", 12345]`. `sort_highscores()` sorts descending via
`highscore_sort()` and trims to five entries.

**e) Persistence.** See below.

`process_mode` is forced to `PROCESS_MODE_ALWAYS` in `_ready()` so the singleton keeps
receiving input while the tree is paused — that is what allows `ESC` to un-pause.

## 5. Save system

Single-line, pretty-printed JSON at `user://minigames.save`:

```json
{
  "game_version": "0.3",
  "breakout_highscores": [["NEH", 21034794], ["---", 0], …],
  "shooter_highscores":  [["---", 0], …],
  "flapper_highscores":  […],
  "game_2048_highscores":[…],
  "snake_highscores":    […],
  "platformer_saves":    { "Nathan": [1, 1, 3, 1, 1] }
}
```

- **Boot order** (`GameState._ready()`): `load_save_file()` → `sort_highscores()` →
  `save()`. Writing on boot normalises an old or partial save immediately.
- **Missing keys are tolerated.** Each highscore key falls back to
  `[["---", 0] × 5]` when absent, so adding a game does not invalidate old saves.
- **`game_version` is the migration hook.** A save without it is ignored from that
  point on.
- **Platformer saves are write-only today.** `save_to_file()` writes
  `platformer_saves`, but the read back in `load_from_file()` is commented out, so
  platformer progress does not survive a restart. A platformer save row is
  `name: [last_world, last_level, lives, coins, current_page]`.
- Saving is triggered from the high score panels after a name is entered or skipped.

## 6. Per-game structure

Every game follows the same shape: a root scene named after the folder, a script with a
`class_name`, and one script per entity type.

| Game | Root class | Entities | State | Status |
| --- | --- | --- | --- | --- |
| Pong | `Pong` | `PongBall`, `PongPlayer` | Score labels in the scene; first to 10 | Playable, 1P (CPU) + 2P |
| Breakout | `Breakout` | `BreakoutBall`, `BreakoutPlayer`, `BreakoutBrick`, `BreakoutPowerup`, `BreakoutSafeFloor` | `level`, `lives`, `points` (setters push to labels) | Playable with high scores |
| Shooter | `Shooter` | `ShooterPlayer`, `ShooterEnemy`, `ShooterBullet` | `start_time`/`time` in ms; survival timer | Playable with high scores |
| Platformer | `Platformer` | `PlatformerPlayer` | `current_world`, `last_completed_*`, `lives`, `coins`, `in_level` | Menu works; only level `1-1` exists |
| Flapper | `Flapper` | `FlapperPlayer`, `FlapperWall` | wall spawn timer only | Walls scroll; no scoring or death |
| Speed Typing | `SpeedTyping` | — | `time`, `record_timehe`, `record_timenl` | Demo; records not persisted |
| 2048 | — | — | — | Empty scene stub |
| Snake | — | — | — | Empty scene stub |
| Math | `Math` | — | `level`, `current_question` | Script only; no scene, not routed |

Notable per-game mechanics:

- **Breakout levels** come from `breakout_levels.tscn`, which holds three children of
  `Marker2D`s. `set_level()` picks `level % 3` and spawns a `BreakoutBrick` at each
  marker with `strength = randi_range(1, level + 1)`, so layouts repeat but difficulty
  climbs. Ball minimum speed also scales with `level`.
- **Breakout powerups** drop with roughly a 1-in-5 chance on brick destruction; the
  weighted table in `breakout_brick.gd::drop_powerup()` covers eight powers, with
  `extra life` deliberately rare.
- **Shooter difficulty** ramps by shrinking the spawn interval every spawn:
  `enemy_spawn_time -= enemy_spawn_time / 69`, starting from 3.0 s. Spawns are rejected
  if they land within 100 px of the player.
- **Pong CPU** is a simple tracker on player 1: move toward the ball's `y` with a 16 px
  dead zone.

## 7. Input map

Actions are declared in `project.godot` and namespaced by game.

| Action | Purpose |
| --- | --- |
| `ESC` | Pause / unpause (handled by `GameState`) |
| `F11` | Fullscreen toggle (handled by `minigames.gd`) |
| `up`, `down`, `left`, `right` | Generic menu/movement (WASD + arrows) |
| `Pong up 1`, `Pong down 1`, `Pong up 2`, `Pong down 2` | Paddle control |
| `Breakout left`, `Breakout right` | Paddle control (mouse also moves the paddle) |
| `Platformer left`, `Platformer right`, `Platformer jump` | Platformer |
| `Shooter left/right/up/down`, `Shooter shoot` | Twin-stick style movement + fire |
| `Flapper jump` | Flap |
| `Speed Typing start timer` | Begin a typing run |

## 8. Conventions

- **Files**: `snake_case.gd` / `snake_case.tscn`, prefixed with the game name for
  entities (`breakout_ball.gd`, `shooter_enemy.gd`).
- **Classes**: `class_name PascalCase extends <Node>` on essentially every script, so
  collisions can be resolved with `if collider is BreakoutBrick`.
- **Indentation**: tabs (Godot default). `.editorconfig` only pins UTF-8;
  `.gitattributes` normalises line endings to LF.
- **Scene node paths**: accessed with `$Path` literals or cached `@onready` vars.
- **Signals**: connected in the editor, landing on `_on_<node>_<signal>()` handlers.
- **Reactive labels**: score/lives use property setters that write straight to the
  label (`breakout.gd`'s `points` and `lives`).

## 9. Known architectural debt

These are structural, not cosmetic; each has a matching item in `backlog.md`.

1. **The old high score panels are orphaned.** `game/high_scores.gd` (`HighScores`) is
   the generic panel introduced in commit `032b0be`, and both `breakout.tscn` and
   `shooter.tscn` now instance `high_scores.tscn`. The per-game predecessors
   (`breakout_high_scores.gd/.tscn`, `shooter_high_scores.gd/.tscn`) are still in the
   repository but nothing references them — safe to delete.
2. **`HighScores` is game-aware via a string.** `set_game("Breakout")` /
   `set_game("Shooter")` maps a name onto the right `GameState` array and the right
   score formatting. Every new game needs a `match` arm there and a `set_game()` call in
   its `show_high_scores()`, or the panel silently has no data.
3. **Entities depend on the singleton, not on their parent.** `BreakoutBall` reads
   `GameState.breakout`, `ShooterEnemy` reads `GameState.shooter.player`. This makes a
   scene unrunnable in isolation (F6 in the editor) and would break if two instances of
   one game ever existed.
4. **Screen bounds are magic numbers.** `1152`, `648`, `1160`, `656` are scattered
   through movement and despawn checks instead of coming from the viewport.
5. **`math.gd` targets an API that does not exist.** It sets `GameState.in_menu`, which
   is not declared in `game_state.gd`, and it has no scene and no menu entry.
6. **Loose scripts at the repository root.** `math.gd` and `line_counter.gd` sit beside
   `project.godot` rather than under `game/` and a `tools/` folder.
7. **No automated tests and no export presets.** Verification is manual play-testing,
   and there is no configured build output.

## 10. Development tooling

`line_counter.gd` is an `@tool EditorScript`. Run it from the Godot editor via
**File → Run** with the script open; it walks `res://`, skips `addons/`, and reports
code lines, comment lines and total lines in an `OS.alert()`.
